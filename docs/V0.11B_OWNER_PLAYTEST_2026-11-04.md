## Room codes: current behavior and proposed direction

Current RoomDiscovery already advertises and resolves nearby LAN rooms using Android NSD. A room row supplies the address/port, but JoinScreen still requires six digits for a first join and HostServer validates them. The digits are a join PIN. They do not supply internet matchmaking. A valid saved guest token already supports rejoining without entering a new code.

The owner's suggestion is to allow hosting with or without a room code. Recommended next UX, **proposed rather than implemented**:

- Open nearby room: choose Host, partner taps the named nearby room and joins the free seat. Recommend this as the home-Wi-Fi default.
- Require a code: a host option for shared networks; selecting the nearby room asks for its PIN. An open room permits another app user on that LAN to take an available seat, so the setting must be clear.
- Manual address is a fallback behind Connection help/Join manually. QR invitation can later fill the endpoint and any required PIN. Never advertise a protected room's PIN in discovery metadata.

Removing the field alone is insufficient. A later implementation must define host admission policy, advertise only the needed room metadata, handle old/new peer compatibility explicitly, preserve existing guest reservations and rejoin tokens, and keep occupied rooms protected from accidental replacement. No product/protocol change is made by this record. A host-approval-only flow is another possible approach, but adds a confirmation step and is not recommended for the initial home-Wi-Fi flow.

Android's NSD guide supports local peer discovery: https://developer.android.com/develop/connectivity/wifi/use-nsd . The release migration must also recheck current local-network access behavior for its chosen target SDK: https://developer.android.com/privacy-and-security/local-network-permission .
